# Cricut Design Space (macOS): native device plugins and the Maker 3

Read-only static analysis of the four plugin executables under `/Applications/Cricut Design Space.app/Contents/Resources/plugins/` (arm64 slices). Tools: rea (Hopper) for pseudo-code and xrefs, `otool`, `nm`, `strings`, `codesign`, plus a small protobuf-descriptor extractor (`scratchpad/tools/protodump.py`) that recovered the embedded `.proto` schemas. Supporting files in the scratchpad: `linkage.txt` (otool -L, entitlements, codesign), `str-*.txt` (strings), `proto-*.proto` (recovered schemas), `nm-*.txt`, `dis-devcommon.txt` (full disassembly of CricutDevice), `pseudo/*.c`, `vtables2.txt`, `opcodes-raw.txt`, `notes-main.md`, and the two per-binary reports `report-devcommon.md` and `report-deviceio.md`. Addresses are arm64 virtual addresses (image base 0x100000000).

## 0. Which plugin is which (corrects the premise)

| Plugin | Identity | Role |
|---|---|---|
| `device-common/CricutDevice` and `device-common-next/CricutDevice` | C++ "bridge" v6.12.13 ("bridge version: {}" near 0x1000af874, "v6.12.13" in str-devcommon.txt), identifier `com.bugsplat.CricutDevice`, stripped | The cutting-machine driver. ## 1. How each plugin talks to the Electron host

All three are child processes spawned by the host (app.asar `PLUGIN_PATHS`: `CricutDevice: ./device-common/CricutDevice`, `CricutDeviceNext: ./device-common-next/CricutDevice`, `CricutVulcanDevice: ./plugin-vulcan/CricutVulcanDevice`, `CricutDeviceIO: ./cricut-device-io/CricutDeviceIO`; `killProcesses`, "Process #"). IPC is stdin/stdout with the same framing in all three: a 4-byte little-endian length prefix followed by one serialised protobuf message. No plugin opens a listening socket, unix socket, XPC service or CFMessagePort (no `_listen`/`_bind`/`_accept`/`xpc_connection_*` stubs in any of the three symbol tables).

CricutDevice (bridge):
- `main` 0x10000af98 (entry 0x100025fe0 is `b 0x10000af98`). cxxopts parser `sub_1000084dc`: `v,version`, `fixbluetooth`, `fixbacklash`, `new-comm-lib`, `msg-timeout-ms`, `crash`.
- Reader `sub_10000814c`: `fcntl(fileno(stdin), F_SETFL, O_NONBLOCK)` (0x100007b50 to 0x100007b7c), `fread` 4 bytes read as `int32` LE, `fread` N bytes with the `msg-timeout-ms` timeout, then protobuf `ParseFromArray` into `NativeModel.Bridge.PBCommonBridge` (`sub_10039e58c`).
- Run loop `sub_10000aa48` stops when `method_action == 13` (`STOP_BRIDGE_MA`). Writer `sub_100007c54`: `[int32 LE length][SerializeToArray bytes]` via fwrite + fflush to stdout (`sub_100199188`), then a 100 ms sleep.
- Envelope `PBCommonBridge` (proto-devcommon.proto lines 136 to 258). Commands are `PBMethodAction` (field 60): `GET_PLUGIN_VERSION_MA=9, GET_OPEN_DEVICE_MA=10, SET_OR_UPDATE_DEVICE_MA=11, STARTUP_BRIDGE_MA=12, STOP_BRIDGE_MA=13, ON_INTERACTION_UPDATE_MA=14, ENUMERATE_MA=15, OPEN_MA=16, CLOSE_MA=17, CLEAR_BUFFER_MA=18, WRITE_BUFFER_MA=19, READ_BUFFER_MA=20, REFRESH_BLUETOOTH_SOCKET_MA=21, GET_DRAW_VECTORS_MA=22, GET_PATH_FROM_VECTORS_MA=23, GET_MACHINE_DEFAULT_STATES_MA=24, SET/GET/ENABLE_LEARNING_MODEL_MA=25..27, EXECUTE_COMMAND_MA=28, SET_MACHINE_MODE_MA=29, GET_MACHINE_MODES_MA=30, GET_COMMAND_LOG_MA=31, DRAW_DEVICE_CUT_PATH_MA=32, EXECUTE_RAW_COMMAND=33, GENERATE_MATCUT_EXECUTION_PLAN_MA=34, ENCRYPT_AES_PATH_MA=35, DECRYPT_AES_PATH_MA=36, DEVICES_ENUMERATE_START=37, DEVICES_ENUMERATE_STOP=38, DEVICES_ENUMERATE=39, DEVICES_OPEN_DEVICE=40, DEVICES_CLOSE_DEVICE=41, DEVICES_OPEN_DEVICE_STATUS=42, DEVICES_OPEN_DEVICE_RESET_BT_MODULE=43`. ## 2. Transport to the machine

Frameworks (otool -L, `linkage.txt`): CricutDevice links Cocoa, IOBluetooth, IOKit, Security, CoreBluetooth, CoreGraphics, CoreText; CricutDeviceIO links IOKit, IOBluetooth, CoreBluetooth, Security, AppKit, libswift* plus bundled asio, libusbp and mdns.c; CricutVulcanDevice links only IOKit, CoreFoundation, libc++ (hidapi bundled).

CricutDevice (drives the Maker family):
- USB: CDC serial. `IOUSBHostDevice` (0x10002db4c) to `IOSerialBSDClient`/`IOCalloutDevice` (0x10002dd48), i.e. `/dev/cu.*` (`CSerialWorker`, vtable 0x100432518). HID only for the bootloader/firmware path (`MacHIDWorker`, IOHIDManager matching at 0x100032b1c to 0x100032b90 with `@"VendorID"`). No vendor ID constant is compiled in: the `VendorID` CFNumber is built from a parameter (`CFNumberCreate` at 0x100032b58 reading `[x29-0x68]`, stored from x1), and enumeration is `device_communication::v2::device_io_context_type::enumerate_devices(const std::vector<VidPid>&, ...)` (RTTI string). A byte scan and a `movz #0x2e24` scan of CricutDevice and CricutDeviceIO found zero hits, so 0x2E24 is not in native code; the VID/PID list is supplied by the Electron host. Errors: "No HID devices with requested VID/PID found in the system." 0x1002e1824, "Device with requested VID/PID/(SerialNumber) not found" 0x1002e1c14.
- Bluetooth: classic RFCOMM only. `IOBluetoothRFCOMMChannel`, `openRFCOMMChannelSync:withChannelID:delegate:`, `IOBluetoothDeviceInquiry`, `IOBluetoothDevicePair`, `performSDPQuery:uuids:` (str-devcommon.txt lines 9018 to 9196; `MacBluetoothWorker`). CoreBluetooth is linked but no `CB*` class or selector string exists, so BLE is unused here. The machine's BT module is a Microchip RN4678 (regex `.*[Rr][Nn]4678.*`, module commands "GX,03", "SQ,D4C1", "SU,03", "SU,00"; "SU,00" referenced at 0x1000da1ec; feature flag `ENABLE_RN4678_INACTIVITY_RESET=28`; `DEVICES_OPEN_DEVICE_RESET_BT_MODULE_MA=43`). `PBConnectionType { BLUETOOTH_CT=1, USB_CT=2, HID_CT=3, BLE_CT=4 }`.
- Serial regex `([A-Z])([0-9]{6})(\w)([0-9]{4})` at 0x10003a2fc (`sub_10003a2d4`); sample table `sub_1000ee0e0`: Q=Athena/Maker, V=Cupid, X=Morpheus, M=Scamander/Maker 3, N=Voldemort, Z=Zeus, D=CupidXL, G=Newt, F=Riddle.

CricutDeviceIO (generic transports):
- BLE: `btle_corebluetooth.Adapter.startScanning(options:)` 0x10016d09c calls `scanForPeripheralsWithServices:nil` (unfiltered); `_btle_adapter_start_scanning` 0x100173dec passes `Optional.none`. TX/RX characteristic UUIDs come from `BluetoothLeSerialTransportParams.tx_characteristic_uuid/rx_characteristic_uuid` (proto 197 to 198) and are validated ("invalid TX characteristic UUID" 0x1001cbad8). localName, manufacturerData and serviceUUIDs are forwarded raw in `BluetoothLeSerialDeviceDescriptor` for the host to filter. No UUID literal exists in the binary.
- USB: `-[UsbSerialDeviceInquirerDelegate runWorker:]` 0x10007ef00 uses `IOServiceMatching("IOUSBDevice")` + `IOServiceAddMatchingNotification`, no VID/PID filter; libusbp `_libusbp_serial_port_create` 0x1001630a8 resolves IOUSBHostDevice to IOSerialBSDClient/IOCalloutDevice (`/dev/cu.*`). `UsbSerialTransportParams { serial_number, vid, pid, interface_number, composite }` come from the host.
- Bluetooth classic: `-[cdio_ChannelDelegate connectDeviceTask:]` 0x100080c28: optional pairing with host PIN, `performSDPQuery:nil uuids:[uuid16:0x1101]` (SPP), `getRFCOMMChannelID:`, `openRFCOMMChannelSync:`.
- TCP: `ip_tcp_adapter_t::start_scan` 0x10000d874 queries `_cricut._tcp.local.` (0x1001cbac4) with bundled mdns.c; port from the SRV record; TXT key "type" (0x65707974) and a 13-byte key (almost certainly "serial_number") read in the lambda at 0x100095394; `IpTcpTransportParams` adds keepalive options.

CricutVulcanDevice: USB HID via hidapi (`IOHIDManagerSetDeviceMatching` with `@"VendorID"`/`@"ProductID"`, pseudo/vulcan-sub_100031d18.c lines 27 and 40); `enumerate_devices` (`sub_10000ab34`) calls `sub_100009adc(ctx, "vulcan pod unit device", "", "", 0x1100, connection_type, cb)`; the VID literal was not recovered.

## 3. Wire protocol to the machine (CricutDevice)

Command objects: each machine command is a C++ class (RTTI names in `devcommon-classes.txt`): `Zorro*Command` for the Explore-era base protocol, `Athena*Command` for the Maker family, `Helium*`, `Morpheus*`, plus `ACKCommand` and `RawCommand`. Send path `sub_1000b4b98` ("sending command 0x{:02X}" 0x1000b4cbc) uses `get_bytes()` (vtable slot 5), `opcode()` (slot 6), retry count (slot 7; generic 15, LoadMat 600) and `parse_response()` (slot 8). Receive path `sub_1000b3410` ("command result: 0x{:02X} {}" 0x1000b366c) branches on machine type at device+0x210: type >= 11 (ATHENA_MT and later, which includes Scamander/Maker 3 = 14) uses `sub_1000b4744`, older types `sub_1000b42c0`.

Framing:
- Zorro family: `[len:1][opcode:1][payload]`. `ZorroNewAESCommand::get_bytes` (0x100060e94) builds 0x32 bytes starting `0x31, 0xC7, ...`.
- Athena family (type >= 11, so Maker and Maker 3): `[len:2 big-endian][opcode:1][payload]`. `AthenaNewAESCommand::get_bytes` (0x10004f360) builds 0x33 bytes `00 31 C7 <(rand%12)+2> <46 random bytes>`; the response parser (0x10004f738) expects big-endian u16 `0x0030` then 48 bytes.
- Responses: first byte/word is the status (0x30 = OK for NewAES); "Unexpected response received from device!" strings per command. Firmware NACK reasons form a ~200-entry enum (str-devcommon.txt lines 4640 to 4840): `INCOMING_CMD_DROPPED, NO_AES_HANDSHAKE, UNKNOWN_ENCRYPTION_REQUIREMENT, DECRYPT_SIZE_ERROR, CRC_ERROR_DURING_DECRYPT, PREDECRYPT_SIZE_MISMATCH, CHECK_SUM_FAIL, BT_UART_FRAME_ERROR, XYMOTION_FAILED_*, SPLINE_PATH_*, VEL_PLAN_*, INTERLOCK_TRIP_* (laser/heat devices), ...`.
- Encryption wrapper `sub_1000394dc` (`encrypt_command_bytes`, device vtable +0x48): pad to a 16-byte multiple, write an 8-bit additive checksum of all preceding bytes as the last byte, AES-256 encrypt (key schedule `sub_10019ba6c` with a 0x20-byte key, S-box 0x1003f34ec, rcon 0x1003f34c0, block loop `sub_10019bd3c` with no chaining visible, so ECB in this path; a second key-schedule caller pair 0x10019a4e8/0x10019a874 likely backs the "CBC AES" variant, string 0x10037d128), then emit `[padded_len | 0x80][ciphertext]`. Opcodes 0x45, 0x46, 0x47 and three exempt classes bypass encryption. On receive, with a key present and device+0xc80 == 1, bytes[1..] are decrypted (`sub_1000b307c`) and the trailing additive checksum verified; mismatch throws "CricutDevice::read_response(CRC Mismatch!)" (0x10037d1dc). The "CRC" is an 8-bit sum; there is no CRC-16 table. The AES-256 key (32 bytes) is stored at device+0x188 by `sub_10005a474`.
- Randomness: `std::random_device` over `/dev/urandom` (0x10004f7e4) seeding a Mersenne Twister (`sub_10004f5ec`).

Opcode table (proven from vtable slot 6; addresses in report-devcommon.md section 3). Shared/Zorro: `0x02 HIDGetStatus, 0x04 HIDErase, 0x05 HIDProgram, 0x08 HIDReset, 0x09 HIDSetPlatform, 0x14 PaperStatus, 0x1a UARTBaud, 0x21 BeginDraw, 0x22 EndDraw, 0x30 SetMachineState, 0x35 ZParamRead, 0x38 GetMaterialDial, 0x3d BluetoothUART, 0x42 DrawVectorFloat, 0x43 MultiDrawVector, 0x60 GetMachineStatus, 0x62 PowerCycle, 0x64 GetCartridgeName, 0x65/0x69 CutTestPatternXYScales, 0x68 AbortCutting, 0x71 ClearButtonState, 0x72/0x78 SetLEDStates, 0x73 GetInterfaceState, 0x76 OrientBlade, 0x77 GetCommandCount, 0x84 LoadMat, 0x85 SimulateButtonPress, 0x88 SetSpeed, 0x89/0x8a Morpheus Set/GetFanSettings, 0xa0 GetPersistentMemory, 0xa1 SetPersistentMemory, 0xa3 CommitPersistentValue, 0xb9 ReadPositionFloat, 0xc3 GetCommMode, 0xc7 NewAES, 0xcf ResetAES / RebootHIDMode, 0xd1 CartridgeLinkQuery, 0xd2 CartridgeLink, 0xe2 EdgeScan / AthenaScanForEdgeFloat, 0xe3 BeginScan/EndScan, 0xe5 BluetoothAlert, 0xee MeasureMaterialOrGetCurrentMeasurement, 0xf0 HomeZAxis / AthenaHomeTheta, 0xff SendZeros`. ## 4. Sequence of a Make, and who does what

Division of labour: the Electron host owns the UI, the material/tool/mat catalogue, the VID/PID and Bluetooth-name tables, and all web calls. CricutDevice (bridge) owns the machine session: enumeration, open, AES handshake, tool detection, mat load, button polling, vector streaming, unload, firmware update. CricutDeviceIO is a transport pipe whose use for the Maker 3 could not be proven from the native side (it has no machine knowledge). CricutVulcanDevice is unrelated to cutting.

Statuses the code proves (OpenDeviceInteraction run `sub_10009be3c`; MatCutInteractionV2 run `sub_10009559c` / step `sub_100095778`; host update handler `sub_100079ad0`):
1. Detect: host sends `DEVICES_ENUMERATE_START/ENUMERATE` (37/39) with a `VidPid` list; bridge replies `device_list` of `PBCricutDeviceSerialized { device_type, serial, connection_type, device_type_enum, bluetooth_name, mac_address, pid, vid, ... }` and `riNoDeviceConnected=101 / riSingleDeviceConnected=103 / riMultipleDevicesConnected=102`; serial regex and name map classify the machine (section 2).
2. Open (v1 `sub_1000704e0`): `riOpeningDevice=104` -> `OpenDevice(key)` (`sub_1000eda34`, "::OpenDevice(key: {})") -> `riDeviceOpenSuccess=105` then `riDialChanged=114`, or `riDeviceOpenFail=106`. v2 (`sub_10009c014`/`sub_1000719b0`) also reports `riOPENDEVICENeedFirmwareValuesSet=1202 / UpdatedFirmwareValues=1203 / GettingFirmwareValuesProgress=1204`, `riOPENDEVICEFirmwareUpdateNeeded=1205`, `riOPENDEVICEMachineRegistrationNeeded=1206`, `riOPENDEVICEGet/SetMaterialSettings=1209/1210`, `riOPENDEVICESystemReport=1215` (`sub_100077244`), and the encryption statuses 1211 to 1214 (section 6).
3. Material and mat: `riWaitingOnMaterialSelected=133` answered by `riMaterialSelected=134` with `material_selected_payload`; mat size from `PBMaterialSelected.mat_width/mat_height` and `PBMatSize`. `riWaitOnMatLoad=110` -> `riMatLoaded=111` (LoadMat 0x84 with a 600-retry wait; `MeasureMaterialOrGetCurrentMeasurement` 0xee for matless/smart-material length; `riMatInMotion=143`, `riMatInMotionInvalidMatLength=145`, `riWaitOnCorrectDeviceStateForLoad=171` with `PBMatLoadDeviceState` listing "Left/Middle/Right Guide", "Mat Support Arms", "Clamp Lever", "Material Sensors", "Pinch Roller Position").
4. Tools: `riSendToolArray=135` / `riToolInfoReceived=136` (`PBBridgeSelectedTools.tools[] PBToolInfo { tool, line, tool_from_api, path_to_points_algorithm }`), `riDetectingTool=137` (AthenaToolDetect 0xea, "DETECT TOOL"), `riMATCUTNeedAccessoryChange=706 / AccessoryChanged=707`, `riMATCUTReportTool=715/716`. Pressure and speed go down as SetMachineState 0x30 / SetSpeedState 0x31 / SetFullToolState 0x3e.
5. ## 6. Licensing, authentication, and what a third-party app would hit

- The machine requires an AES session before it accepts most commands: NACK reasons `NO_AES_HANDSHAKE`, `UNKNOWN_ENCRYPTION_REQUIREMENT`, `CRC_ERROR_DURING_DECRYPT`. The handshake command is `NewAES` 0xC7 (Athena form: `00 31 C7 <(rand%12)+2> <46 random bytes>`, reply `00 30` + 48 bytes), with `ResetAES` 0xCF. Once a 32-byte key sits at device+0x188, every command except opcodes 0x45/0x46/0x47 is AES-256 wrapped with an 8-bit checksum (section 3).
- Where the key comes from: not local maths alone. `OpenDeviceInteraction::update` (`sub_100079ad0`) stores `PBCommonBridge.base64_devices_hello_key_response` on status `riOPENDEVICEEncryptionSetHelloWebResponse=1212` (interaction+0x868) and `base64_devices_key_response` on `riOPENDEVICEEncryptionSetWebResponse=1214` (interaction+0x880, flag +0x899). The matching requests are `riOPENDEVICEEncryptionGetHelloWebRequest=1211` and `GetWebRequest=1213`, carried to the host as `PBWebRequest { action, parameters, method, body }` with `PBDevicesHelloRequest { type, id }` and `PBDevicesResponseRequest { type, response, hello }`; the host performs the HTTPS call (the plugin has no network client for this). The 48-byte machine nonce plus the server's base64 payloads produce the session key. Also present: `riCLNKEntitle=901 / EntitleResult=902` (cartridge entitlement) and `riOPENDEVICEMachineRegistrationNeeded=1206`.
- No RSA, certificate, signature or firmware-cert code exists in any plugin (no CommonCrypto/SecKey/HMAC/SHA stubs; only `SecTrustedApplicationGetTypeID`). Judgement: the barrier for a third-party app is a server-held secret exchanged through Cricut's cloud at device-open time (hello/response round trip keyed on machine identity and nonce), not a local check that could be patched out. Without that exchange the machine answers `NO_AES_HANDSHAKE` and drops commands. Firmware updates (`FirmwareUpdateV2Interaction`, `[FWUPv2]` strings, HID bootloader opcodes 0x02/0x04/0x05/0x08/0x09) are fed from the host (`firmware_file`), so firmware signing, if any, is enforced by the machine bootloader and was not observable here.
- CricutDeviceIO and CricutVulcanDevice contain no crypto; Vulcan reports `ERROR_DEVICE_AUTH_FAILED` and an `activated` flag, implying its device-side auth lives in the pod firmware or the host.
