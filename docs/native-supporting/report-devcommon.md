# CricutDevice (device-common, bridge 6.12.13, arm64) findings

Working files: scratchpad/pseudo/*.c (Hopper pseudo-code per procedure), vtables2.txt (typeinfo to vtable map built from dyld_info chained fixups by vtab.py), opcodes-raw.txt (per-class opcode getter), fixups.txt.
Hopper crashed twice mid-session; everything below was re-verified after reopen.

## 1. Host IPC framing (stdin/stdout, no sockets)

- main 0x10000af98 -> sub_10000ab78(argc, argv, dispatch=sub_10000a970). sub_1000084dc parses argv with cxxopts (regex "--([[:alnum:]]...)" at 0x10001b110). Options: "v,version" (0x100008614), "fixbluetooth", "fixbacklash", "new-comm-lib", "msg-timeout-ms", "crash" ("Crash the application for testing purposes"), plus "[OPTION...]"/"positional parameters". dword_10045a15c==1 selects the new-comm-lib callback set (sub_1000afb3c vs sub_1000af93c).
- Reader sub_10000814c: fcntl(stdin, F_SETFL, O_NONBLOCK); fread 4 bytes -> int32 little-endian length N (read as *(int32_t*)), then fread N bytes with a timeout of qword_10044f228 ms ("msg-timeout-ms"), then sub_10039e58c = protobuf ParseFromArray into PBCommonBridge. Timeout logs via sub_10019902c(level 7).
- Run loop sub_10000aa48: while running flag byte_10044f1e0: read message; if method_action (var_74) == 0xd (STOP_BRIDGE=13) -> sub_1000af570 and stop; else dispatch sub_10000a970 -> sub_1000af3d8 -> sub_10006a68c (bridge dispatcher, mutex-guarded) under qword_10045a400 (bridge singleton). Dispatcher logs "client: {}" and sends replies with sub_100069a30.
- Writer sub_100007c54: mutex, SerializeToArray (sub_1001e4f64, error string "inMessage.SerializeToArray FAILED"), writes [int32 LE length][bytes] via sub_100199188 = fwrite+fflush to ___stdoutp, then sleeps 100 ms (0x5f5e100 ns).
- No _socket/_listen/_bind/_accept/xpc_*/CFMessagePort stubs exist in the binary (grep of "symbol stub for:"). The only IPC is stdin/stdout.
- Logging: sub_1000f06e0 calls getenv("ENABLE_BRIDGE_LOG_FILES") at 0x1000f08a4; level = 0 if set else 6 (spdlog off) via 0x1002e7664. Path built by sub_1000f2af4: <base from sub_100198edc>/logs/bridge.log. So it is an environment variable, not a feature flag.

## 2. Machine wire protocol

Send path sub_1000b4b98 (contains "sending command 0x{:02X}" 0x1000b4cbc):
- cmd->get_bytes() = vtable slot 5 (+0x28); opcode = slot 6 (+0x30); slot 7 (+0x38) = retry/timeout count (generic 0x100036134 returns 15; LoadMat 0x10004ac48 returns 600); slot 8 (+0x40) = parse_response.
- Encryption gate: if device+0x188 (r20[0x31], AES key pointer) != 0 and opcode not in {0x45,0x46,0x47} and command not a dynamic_cast to three exempt classes -> device->encrypt_command_bytes (device vtable +0x48 = sub_1000394dc for Zorro/Athena family). Opcodes 0x40/0x41/0x42 skip a pre-send callback (qword_10045a548).
- sub_1000394dc (encrypt_command_bytes): calloc(len padded up to 16 with room for 1 byte), copy plaintext, write an 8-bit additive checksum (sum of all preceding bytes) into the last byte (NEON addv loops), AES-encrypt with sub_100199fc4(key=device+0x188), then output = [1 byte header = padded_len | 0x80 (flag set unless an accumulated-counter condition fails)] + ciphertext.
- AES: sub_100199fc4 -> key schedule sub_10019ba6c(key, 0x20) = AES-256 (key sizes 16/24/32 accepted, S-box at 0x1003f34ec, rcon at 0x1003f34c0), then per-16-byte block sub_10019bd3c with no chaining visible => ECB in this path. Decrypt sub_1000b307c -> sub_10019a1bc (same key schedule, block decrypt sub_10019c124, strips trailing zero padding). Other key-schedule callers 0x10019a4e8 / 0x10019a874 exist (likely the "CBC AES" variant, string at 0x10037d128) but were not decompiled. No CommonCrypto/OpenSSL/RSA/certificate stubs exist (only SecTrustedApplicationGetTypeID); no signature check anywhere.
- Receive path sub_1000b3410 ("command result: 0x{:02X} {}" 0x1000b366c): machine_type (device+0x210, r20[0x42]) >= 11 (ATHENA_MT) -> sub_1000b4744, else sub_1000b42c0 (older Zorro family). Both: raw read (sub_1000b33ac / sub_1000b4068), then if key set and device+0xc80 (encryption enabled) == 1 -> decrypt bytes[1..] and verify last byte == 8-bit sum of the rest; mismatch -> throw "CricutDevice::read_response(CRC Mismatch!)" (0x10037d1dc). So the "CRC" is an additive 8-bit checksum, no CRC-16 table.
- Framing by family (from get_bytes builders): Zorro family 1-byte length then opcode; Athena family (machine type >= 11) 2-byte big-endian length then opcode. Evidence: ZorroNewAES bytes (0x100060e94) = 0x32 bytes starting [0x31, opcode...]; AthenaNewAES bytes (0x10004f360) = 0x33 bytes starting [0x00,0x31, opcode 0xC7, (RandomByte()%12)+2, 46 random bytes]. Response parse: Zorro expects first byte 0x30 (0x100061110), Athena expects first u16 BE == 0x30 (0x10004f738), then copies the 48-byte payload; otherwise throws "New AES - Unexpected response received from device!".
- Randomness: RandomByte() (sub_10004f5ec) = std::random_device (/dev/urandom, sub_10004f7e4) seeding a Mersenne Twister (0x6c078965 init loop) + uniform_int_distribution.
- Key establishment, what is proven: the device stores a 32-byte AES-256 key at device+0x188 via sub_10005a474 (malloc(0x20) + copy, ZorroDevice vtable slot 11). The NewAES command (0xC7) sends 48 random bytes and the machine answers 0x30 + 48 bytes. Host side: OpenDeviceInteraction::update (sub_100079ad0, via vtable slot 5 0x10009be18) handles status 1212 (0x4bc) by copying PBCommonBridge.base64_devices_hello_key_response (field slot r20[0x33]) into interaction+0x868 and status 1214 (0x4be) by copying base64_devices_key_response (r20[0x34]) into interaction+0x880 and setting flag +0x899. Status 1215 (0x4bf, SystemReport) is set in sub_100077244. What is NOT found: any code that stores 1211 or 1213 (0x4bb/0x4bd) into the status field or any immediate 0x4bb/0x4bd anywhere in the arm64 text (only enum tables in __DATA at 0x1004e5f60/0x1004e6a5c). The open sequences I decompiled (sub_1000704e0 v1, sub_10009c014 and sub_1000719b0 v2) only emit 104/105/106/114 and 1203/1204. Conclusion: in this build the handshake plumbing (hello -> server -> key) exists on the receive side, but the request emission and the exact derivation of the 32-byte key from base64_devices_key_response and the 48-byte machine nonce were not located; the key is a server-held secret delivered through the host's PBWebRequest, with no RSA or certificate check in the plugin.

## 5. Transport selection and Maker 3 identity

- Machine type lives at device+0x210 (r[0x42]). Serial sample table sub_1000ee0e0 keyed by it: 11 ATHENA -> "Q200101I1234", 12 CUPID -> V, 13 MORPHEUS -> X, 14 SCAMANDER -> M, 15 VOLDEMORT -> N, 16 ZEUS -> Z, 19 CUPIDXL -> D, 22 NEWT -> G, 23 RIDDLE -> F, plus "H000000IU0000", "CMP000000I10000", default "QYYMMDDI1234". Serial regex "([A-Z])([0-9]{6})(\w)([0-9]{4})" parsed in sub_10003a2d4.
- Name map sub_10003db20: "maker3" (and "scamander") -> 0xe = SCAMANDER_MT (14). So Maker 3 = SCAMANDER_MT, serial prefix M, class ScamanderDevice (vtable 0x100433bc0, same V2 family as Cupid/Zeus/Newt/Riddle/Voldemort); "athena"/"maker" -> ATHENA_MT 11 (AthenaDevice, prefix Q).
- Transports: IOBluetooth classic only (IOBluetoothRFCOMMChannel, openRFCOMMChannelSync:withChannelID:delegate:, IOBluetoothDeviceInquiry/Pair delegates in str-devcommon.txt lines 9018-9196); CoreBluetooth is linked but no CB* class or selector strings exist, so BLE is not used. RN4678 strings "GX,03"/"SQ,D4C1"/"SU,03" sit in a string table (0x10040c761, no code xrefs) and "SU,00" is used at 0x1000da1ec; inactivity reset gated by log strings at 0x100038960/0x1000389f8. USB: IOUSBHostDevice / IOSerialBSDClient CDC serial (CSerialWorker vtable 0x100432518), HID bootloader via MacHIDWorker (vtable 0x100432608, IOHIDManager VendorID matching 0x100032b64).

## 6. Make sequence (what the code proves)

- OpenDeviceInteraction vtable 0x100439c80: run = sub_10009be3c -> sub_1000776fc (v1) or sub_10009c014 (v2, when interaction+0x3208 == 1). v1 open sub_1000704e0: status 104 riOpeningDevice (r19[0x185]=0x68) -> device OpenDevice(key) sub_1000eda34 ("::OpenDevice(key: {})", key = device handle string, feature checks 0x65/0x66) -> on success 105 riDeviceOpenSuccess then 114 riDialChanged; failure 106. v2 path reports 1203/1204 (firmware values) repeatedly. sub_100077244 reports 1215 SystemReport.
- MatCut: the run loop above; host-driven statuses 718 to 721 (present carriage, simulate load/cricut/pause button) and 729 are handled in sub_100079ad0; 701 NeedPathData -> 704/705 processing -> 725 UseV2 -> 727 CompleteSuccess are emitted from sub_100095778 range. Explicit per-step machine command order (status, serial, firmware, AES, tool detect, load mat, go) was not recovered because commands are created through virtual factories (sub_10004b268) and dispatched through device vtables; the opcode table in section 3 is the reliable map.
